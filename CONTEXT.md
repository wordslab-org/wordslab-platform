# CONTEXT — Wordslab Platform (home-scale AI platform)

Working vocabulary for the effort. Home of the design conversation; the spec it produces lives in this repo's docs.

## Glossary

- **Platform** — the whole system: a local AI platform, 100% built from open-source components and models, aimed at AI enthusiasts at home and small businesses who want to own their intelligence. Deployed in a trusted environment at very small scale. Simplicity is the main feature.
- **Service** — an independent, composable component of the platform (document, audio, image, chat, agent, workflow, ...). Each service has its own database, business logic, UI, and API, and can run fully independently — on this machine, on another machine, or in the cloud. A service can be **model-backed** (chat), **tool-backed** (web search), or both.
- **LLM inference service** — *(superseded — see **Inference service** below)*
- **Inference service** — the unique model-serving engine (prod): 3 capabilities sharing one contract surface, one `/v1/models` lifecycle (download/load/unload/prepare, RAM-cached weights), one resource budget — **llms** (family 1 Responses API + family 5), **diffusion** (family 2 images/videos, ComfyUI behind a thin MIT bridge), **classic AI** (family 2 predict-style: classify/detect/segment/extract/predict for trained models of all modalities). Every model-backed service rides it over HTTP; multiple instances = model routing, not contract.
- **Training and Evaluation service** — the dev-side counterpart to the Inference service: train/fine-tune for all three model classes (LLM LoRA via Tinker-by-reference, diffusion adapters, classic models via fastai), dataset prep (gather/version/anonymize), publish trained models → Inference service, **plus the evaluation capability** (renamed from the Training service by ADR-0013 §6; evaluation content = ADR-0020, #16). Notebooks (Dev service) are its human surface. *(Training half = #30, open; evaluation half = ADR-0020. Full job-runner form v1.1; v1 = notebook-driven + dataset APIs + model upload.)*
- **Chat + Agents service** — the platform's agentic front door: chat sessions, agent authoring, agent runs, memory, workspaces and harness images. Human surface = Open WebUI (vendored); default stateless harness = MAF (in-process, Python); containerized harness images (Hermes Agent, OpenCode, Pi) for workspace sessions; sessions two-tier (structured DB for MAF, opaque harness home for images).
- **Workflow service** — composes and schedules/triggers all platform capabilities. A workflow **is a Python program** (the source of truth) using a tiny set of **composition primitives** (`call`/`model`/`agent`/`subworkflow`/`delay`/`event`/`user_input`); branch/loop/transform are plain Python control flow. Authoring = code, aided by an agent-chat companion; a **read-only visual view** shows steps + flow logic (no editable canvas in v1). Runs/schedules/triggers, retries, state persistence, unattended or async-human-input runs.
- **Development service** — pro-code + agentic dev environments: capabilities **code-server** (VS Code + Kilo Code), **JupyterLab**, **agentic development workflow** (a UI embodying the modern agentic AI dev workflow — Matt Pocock engineering skills: wayfinder/grilling/tdd/code-review… — used to develop the platform's own services). Publishing the result of a development activity → the combined **Publishing & Governance service** (#21 / ADR-0019). Not model-backed: AI extensions are clients of the agent service. Opens the same workspace directories the agent service manages.
- **Audio service** — the platform's voice surface: capabilities stt (batch), stt-realtime (streaming), tts (batch), tts-streaming, vad, voice cloning & design, and realtime voice chat (family 4, WebRTC) — which composes stt-realtime + tts-streaming + vad locally but is driven by the **agent service** (tools, skills, sessions), not plain LLM inference. Dictation (mic → stt-realtime → text) is a shared UI-kit affordance every service with long-text inputs gets.
- **Image service** — capabilities generate (text-to-image), edit (image-to-image/inpaint), video (async text/image-to-video; ComfyUI behind a thin MIT bridge). Models in `models.toml`: commercial-safe defaults (FLUX.2-klein-class, Apache) + license-gated (FLUX-dev, MiniMax H3, SDXL). Image/video generation is also a **first-class agent tool** (MCP via registry #20) and **integrated in the Chat + Agents UI**, plus its own standalone gallery/prompt UI.
- **Document service** — expert in raw **document bundles**: ingest/parse (structured markdown · schema-driven JSON · docling format · image rendering for complex pages), organize (bundle-level classification/sorting/splitting/merging), index (multilingual · late-interaction · multimodal), search/retrieval (collection + single long document, reranker + hybrid lexical/semantic + structured-property filters), **bundle-level structural operators** (merge/check/format/order, same DocETL syntax), a rich configurable **document search agent** (partnership with the agent service). Owns the raw bundle data and its indexes; each individual document inside a bundle is still tracked as its own index entry. Splits with the **Knowledge service** (#26): this service keeps parsing/extraction/indexing/retrieval of raw bundles; Knowledge takes the reasoning/ontology/knowledge-graph side. Creation/output is the Generation service's job.
- **Knowledge service** — expert in *reasoning over* document bundles to produce derived knowledge: **ontologies / concepts**, **entity resolution + grounding** (to canonical concept/entity IDs), **knowledge-graph building**, **cross-document-set aggregation**, **facts extraction**, a **transversal semantic view** (references into documents, tied to no single document), and the **bridge to the structured information system** (systems of record). Owns only the *derived* knowledge (ontologies, concept graph, entity repository, knowledge base) — which **references** document bundles by stable ID (`document.<bundle>`), never copies their content. Runs the **DocETL abstract-request engine** (#24 / ADR-0010) — two modes (simple execution + stored procedure lifecycle), dispatching **faithful-representation** steps to the Document service where the data lives and keeping the interpretation/reasoning in Knowledge; hosts entity resolution / concept repository / knowledge-graph building (#25). Inbound read/query via the base contract; outbound exports to external IS apps go through the **Connectors service** (single audited door). The bridge's boundary to the user: "my documents" (Document) vs "the knowledge we built from them" (Knowledge). *(Added by the Document/Knowledge split, #26.)*
- **Document bundle** — a coherent collection of related raw inputs that arrive together and make sense as one unit: an email + its attachments + history; a meeting's transcript + invitation + attendees + agenda + presentations; a set of scanned paper documents found in a physical envelope. May be **multi-modal** (audio transcription, text agenda, images of slides, a word-processor study), where the textual representation may be **produced by another service** (audio transcription, image description) and assembled by the Document service. The **unit of organization** (format/order/normalize) and, in some flows, of **search** — while each individual document inside is still tracked as its own index entry. *(Added by the Document/Knowledge split, #26.)*
- **Knowledge capture** — the progressive capture of **enterprise knowledge demonstrated by employees in human-in-the-loop agent sessions** (a.k.a. progressive enterprise knowledge capture). The validated deltas of a session (what an employee **corrected** or **confirmed** — incl. implicit confirmations) are logged via **delta logging** as **proposed knowledge items**, each carrying full **provenance** via the action-context (which session, which employee, when, corrected from→to). *Capture, not extraction* — the system records that a human changed something; the truth claim is validated only at review. Nothing enters the knowledge base implicitly: items go to the **review queue**, a human approves each, and only then is it reasoned into its destination — **facts/entities** → the Knowledge service concept/entity graph (grounded); **exact repeated procedures** → the Workflow service (the agent→workflow graduation path); **reusable approaches** → a **skill**. The raw evidence for every item is a document bundle in the Document service, so every captured fact traces to its source. *(Added by the Document/Knowledge split, #26; mechanism refined by ADR-0012, #27.)*
- **Agent memory** — the memory content of the agent system: user identity & profile, job & role, knowledge & skill level, preferences, current-task context, procedural knowledge for the job. Backed by the **Document** service (raw memory artifacts as document bundles) plus the **Knowledge** service (reasoned profile/knowledge graph, semantic retrieval feeding agent context), not bespoke storage; the agent loop itself stays in Chat + Agents (working memory). *(Added by ADR-0012, #27.)*
- **Memory substrate** — the storage/reasoning split that backs agent memory: **Document** stores the **raw episodic** memory as **document bundles** (conversation-transcript bundle, user-profile dossier of verbatim stated facts, task-history bundle — non-lossy, source of truth); **Knowledge** *derives* the reasoned memory (compact user-profile summary, the profile/graph, grounded skills) lazily/asynchronously, each derived item tracing back to its bundle IDs. *(Added by ADR-0012, #27.)*
- **Episodic memory** — the raw layer of agent memory: records of past events/experiences ("what happened, when") — the Document bundles (conversation transcripts, task history). Keep it non-lossy and source-of-truth; summaries are separate derived artifacts. *(Added by ADR-0012, #27.)*
- **Semantic memory** — the reasoned layer of agent memory: distilled facts, the user profile, concepts/knowledge graph ("what is true"), derived by the Knowledge service from the raw bundles; retrieved on demand, can go stale, must trace back to raw. *(Added by ADR-0012, #27.)*
- **Procedural memory** — how to do the job: skills, rules, instructions, mapped to concepts by the Knowledge service; the *explicit, versionable* form of procedural knowledge (distinct from facts). *(Added by ADR-0012, #27.)*
- **Working memory** — the agent loop's context window in Chat + Agents; the current-task context the agent is actively thinking about. Memory is *pulled into* working memory on demand (memory is context engineering). *(Added by ADR-0012, #27.)*
- **Memory retrieval** — the act of pulling long-term memory into the agent's context: a callable capability (owned by Document + Knowledge) composing the `chunks` and `graph` data sources with an explicit precedence order, returning **cited, provenance-linked** context; supported by a small preloaded profile/current-task surface; natural-language answers over memory are an **agentic search tool**. Deterministic and observable. Default = preloaded + agent-invoked. *(Added by ADR-0012, #27.)*
- **Proposed knowledge item** — a record of a **validated delta** captured from a HITL session, awaiting review: carries a provisional kind (FACT / ENTITY / PROCEDURE / APPROACH), the delta `{from → to}`, and provenance via the action-context. Status `PROPOSED`. It flows into the **review queue** (shared with #25); a human approves, rejects, skips, creates-new, or edit-then-promotes it before it is routed. *(Added by ADR-0012, #27.)*
- **Delta logging** — the capture mechanism: recording the *minimal change* a user made in a session (a correction `from → to`, or a confirmation, incl. implicit), not whole turns. Run as a DocETL pipeline on the Knowledge engine: extract deltas from the transcript bundle → resolve mentions via `knowledge.entities.resolve` → propose to the review queue. *(Added by ADR-0012, #27.)*
- **Capture routing** — classifying a captured item to one of three destinations by nature, on the one-axis **determinism** test, **reviewer-confirmed**: **facts/entities** (a true statement) → Knowledge graph; **exact repeated procedures** (always the same way) → Workflow service (graduation path); **reusable approaches** (human improvises each time) → a skill. The agent may suggest; a human disposes. Re-routing is a normal lifecycle event. *(Added by ADR-0012, #27.)*
- **Generation service** — document/report/website *creation*, the output-side counterpart to the document service: reuses all other services (connectors for sources, agents for drafting, workflow service for reusable pipelines, document service for dataroom/references, inference for models) and combines them in two ways: (1) an interactive, open authoring experience for one-shot documents/reports/websites, (2) user-built, workflow-assisted generation experiences for recurrent needs (e.g. a monthly GitHub-activities summary). Content drafted as HTML/CSS artifacts, exported to docx/xlsx/pptx/pdf. Publishing a generated website → the combined **Publishing & Governance service**'s publishing surface (#21 / ADR-0019).
- **Media transformations service** — ships ready-to-use transformation capabilities across numeric/text/images/audio (data cleaning, datetime normalization, translation, summarization, face recognition/redaction, moderation, anonymization, language detection, guardrails, entity detection): the most frequent transforms built-in to accelerate home projects.
- **Capability** — a sub-service inside a service: an in-process module that owns its business logic, models, routes, and UI pages, while sharing the service's contract surfaces (one `/health`, one auth, one `/mcp`, one OpenAPI) and its database. E.g. the audio service's capabilities: stt, tts, vad, voice cloning, realtime voice chat. A capability may be promoted to its own service if it outgrows its group.
- **Connectors service** — the platform's single way to connect to the digital world: exposes external web services and the user's own applications as callable tools (MCP via registry #20), with a security/audit/approval layer over every outbound call (what leaves the machine is logged; sensitive connectors require approval). **v1 connectors**: web (search + fetch) · x/twitter · outlook mail · youtube (search + extract) · github · huggingface. Post-v1 seed catalog (from Hermes Agent built-ins): browser automation, home assistant, spotify, discord, feishu, yuanbao, generic user-app APIs. May also host a network gateway / reverse proxy for external clients (inbound exposure of published apps). *(Gateway timing: v1.1 per #21 / ADR-0019 — v1 exposes published apps on the LAN + a private-mesh overlay (Tailscale/WireGuard, node inside WSL2, Publishing auto-manages default-deny one-app-to-device ACLs); the public-internet gateway is v1.1 and implements ADR-0017's browser-aware TLS + edge-auth. Its outside-world credentials come from the core's `secrets` capability, machinery #14 / #19.)*
- **Capability registry** — the platform's searchable index of everything an agent loop can discover and load at runtime, and the **name→URL resolver** for all composition references. **Thin index + name authority on the leader core**: entries are `tool | api | agent | workflow | skill | data_source | webapp` (seven types — `api` and `webapp` added by ADR-0019 for published things), each holding `id` · type · one-line description (with privacy label `local`/`cloud_no_data`/`cloud` where applicable) · a reference to the **owning service** (which stores the full definition, fetched on demand). **Models are deliberately not in it** — the model catalog lives in the model lifecycle family and the model management layer. One registry, two consumption modes: **search/load** (a hardcoded core primitive; agents search within their server-side-enforced **accessible tool set**, the allowlist living in the agent definition) and **resolution** (workflows reference explicit stable names, no search). The **core's registry is the name authority** — it validates, reserves, and 409-rejects collisions, so a published name is a stable, immutable reference. Shapes: docs/adr/0008.
- **Service contract** — the set of API conventions a service must follow to be a platform service: a **base contract** applying to every service API, plus the **family contracts** the service's function requires. The service template embodies it.
- **Base contract** — the minimal conventions every service API follows: transport (HTTP+JSON, SSE for streaming), auth (per-service Bearer API keys, v1, + admin-scoped key-management surface), versioning (`/v1` prefix), errors (one JSON shape + fixed taxonomy + `request_id`), cursor pagination, `/health`, optional `Idempotency-Key`, the usage-accounting principle (uniform `usage` field; unit defined per family), the **action-context header** (action id + user + service chain, propagated through chained calls), and the **log surface** (`GET /v1/logs` — common filters + per-service `q` search, scoped by key scope + user).
- **Family contract** — the conventions for one family of service capabilities (LLM & agents inference, other model inference, tool services, realtime, async jobs & model lifecycle, batch, uploads, webhooks, authoring & management). A service implements the base contract plus only the families its function needs; plain CRUD services get the base alone.
- **Platform core** — the single centralized service of the platform (sharpen of the earlier "Platform services (centralized)" candidate): one base-contract service per machine, with capabilities `fleet` · `install` · `catalog` · `resources` · `backup` · `users` · `keys` · `secrets` · `monitoring` · `logs` · `stats` · `datasets`. It centralizes **control — never data, execution, storage, or the request path**: services run fully standalone with the core down; the core is the platform's eyes, hands and ledger. Its human surface is the dashboard. The first machine's core is the **leader core**; other machines run **worker cores** (same service, capabilities enabled per role). Shapes: docs/adr/0003.
- **Dashboard (integrated UI)** — the platform core's human surface and the platform's **single human front door**: a role-aware shell that groups the platform's **four feature sets** (Ops · capability explorer · builder · always-on metrics incl. cloud spend) under **three views** — **Administrator** (admin-only: install/config/update/backup, machines, cloud, users, registry, activity) · **User** (everyone: a simple UI for the capabilities of all services) · **Builder** (everyone: Development, agent builder, workflow builder, app publishing, authored registry) — gated by the settled `admin`/`member` level (not new permission levels). Hosts **the UI of every service capability**, not just the core's. Editor-style layout: left + top bars = navigation, bottom = status bar, always-on metrics = a narrow **right rail** (GPU/VRAM + CPU/RAM primary, cloud % spent when in use, disk de-emphasized; hover → floating card, click → full-metrics screen). Weaves an **educational guidance layer** through every surface (thin by default, deep on request). Hosts the initial install web UI + first-run welcome. Deep management; the **resident launcher** is the machine-lifecycle + connect surface; no duplicated surfaces. Shapes: docs/adr/0015.
- **Bootstrap layer** — the native, platform-specific machinery *below* the service contract: installs/updates WSL + a Linux distro + virtual disks on user-chosen physical disks (wordslab-notebooks pattern), installs uv + Python, verifies network reachability (github/pypi), installs the first platform core, then hands off. Persists as a re-runnable native updater for its own layer; not a service (no API, no DB, no keys).
- **Community catalog** — the **discovery/submission** surface for community services: a **git repo** of thin catalog *listing* records (see **platform.toml**), where third-party/community services are submitted and browsed. The **official one lives on the `wordslab-org/wordslab-platform` GitHub repo** (a page/directory of the most popular community packages); **anyone can host their own catalog repo**. A machine points at a catalog *source* — default the official repo, changeable to any other. Distinct from the core's `catalog` capability (per-machine installed/available inventory) and the **capability registry** (runtime name authority): the flow is *community catalog → user chooses → core `catalog`/`install` (ADR-0016) → runtime registry (ADR-0008)*. *(Added by ADR-0018, #15.)*
- **platform.toml** — the **catalog repo's thin index of listing records**; one per catalog repo. *(Renamed from `catalog.toml` by ADR-0019.)* Each record points to a **description** (`service.toml` / `implementation.toml`) living in a **source repo**, and carries: name + type (`service` vs `implementation`), source/attribution (which catalog + source repo), **version + checksum** of the referenced package, license, and a copied description for browsing — the source description is the reference at install. At a **project** root it is the same file declaring that project's **platform services/implementations** (regime 1, ADR-0019 §5/§6). TOML, consistent with the platform. *(Renamed by ADR-0019, #21.)*
- **implementation.toml** — the named declaration file for an **implementation** (a concrete way to deliver an existing capability), symmetric with `service.toml`: identity, source (local weights or cloud provider reference), license, links, download/disk sizes, resource profile, privacy tier. Lives in the owning source repo; the authoritative definition at install. *(Formalized by ADR-0018, #15; sharpens ADR-0002 §5.)*
- **Bundled service** — a service (or implementation) whose code lives **in the `wordslab-platform` repo itself**: it ships with the platform, appears in the v1 catalog on install, and the platform **takes on updating/maintaining it with the bundle** (ADR-0016 Tier 2/3). The strongest of the three **review-status levels**. *(Added by ADR-0018, #15.)*
- **Listed service** — a service (or implementation) implemented **in another repo** but **referenced in wordslab-platform's `platform.toml`**: accepted via PR + light maintainer look into the official community catalog. The middle **review-status level**. *(Added by ADR-0018, #15.)*
- **Third-party service** — a service (or implementation) implemented elsewhere and **not referenced** by wordslab-platform's catalog: living in someone else's catalog repo, **not reviewed by the platform at all**. Installable, but visibly unvetted. The third **review-status level**. *(Added by ADR-0018, #15.)*
- **Review status** — a catalog entry's status, **computed never declared**, as a pure function of code location + official-catalog membership: **`bundled`** (code in the wordslab-platform repo) / **`listed`** (referenced by wordslab-platform's `platform.toml`) / **`third-party`** (neither). No status field to drift or lie. *(Added by ADR-0018, #15.)*
- **Graduation** — the deliberate, **conservative, maintainer-decided** step by which a community service becomes a **bundled service**: the maintainer decides it is ready at a higher bar (proven usage/demand, stable well-formed API, well-maintained, passes the conformance/safety bar) and commits to maintaining it with the bundle. **Not automatic by popularity** — usage is a signal, not a rule. *(Added by ADR-0018, #15.)*
- **Compliance catalog** — the **governance half** of the combined Publishing & Governance service: the **platform-side, per-machine audit view** of what's installed and run (services, capabilities, implementations, published apps/workflows), each carrying its compliance facts — version + update status, license, privacy tier, supply-chain scan status, resource usage, and **computed review status**. Surfaced in the dashboard's **Administrator view** (ADR-0015) as "what's on my platform and is it compliant", **read-only**. The **Builder view** shows the same compliance facts **authoring-mode for the builder's own developments** (editable/improving — compliance is the builder's responsibility). Compliance is **coupled to publishing** (ADR-0019 §8): it is only mandatory at the **act of publishing**, not during development. Distinct from the **community catalog** (discovery side). *(Added by ADR-0018, #15; authoring/regulatory dimension by ADR-0019, #21.)*
- **Published thing** — the packaged, deployed, exposed **result of a development activity** — code (written or generated) or agent/workflow configuration. **Light by default**: NOT automatically a full base-contract platform service (ADR-0019 §1/§3). Runs as a **static site** (served files) or a **long-running container** (no serverless in v1); its runtime is picked explicitly, never auto-detected. Composable things (API/tool/agent/workflow/UI) **register** in the registry (one entry per surface exposed; a UI registers via **webMCP**). *(Added by ADR-0019, #21.)*
- **Project** — the shared unit of the Development and Publishing services: a **GitHub (or local) repo** backing a unit that can contain **all types of publishable artifacts** (code or config). At its root: **`platform.toml`** (the project's platform services/implementations) + **`publish.toml`** (the project's generic publishable APIs/apps/agents/tools). *(Added by ADR-0019, #21.)*
- **publish.toml** — the project-root manifest declaring the project's **generic publishable APIs/apps/agents/tools** (regime 2, ADR-0019 §5/§6) — the small-scale family/demo/learning things, author-versioned, with **no** adherence to platform versioning/update mechanics. Sits beside `platform.toml`. *(Added by ADR-0019, #21.)*
- **Deployable-packages catalog** — the **real surface of the Publishing service** holding the **generic published things** (regime 2): a catalog of deployable packages sourced from **GitHub + local repos**, where the user **deploys/undeploys** and **starts/stops** each, author-versioned. Separate from the platform's ADR-0016 update machinery and from the compliance catalog's audit purpose. *(Added by ADR-0019, #21.)*
- **webMCP** — the protocol by which an agent can **drive a published web UI** (manipulate a webapp), which is why a `webapp` UI registers in the registry (an agent-drivable surface). *(Added by ADR-0019, #21.)*
- **Compliance checklist** — the regulatory-posture side of a published thing's compliance (ADR-0019 §8): the **European AI Act + GDPR** requirements summarized into a **simple checklist/set of questions the author answers**, structured so the **first questions give a short exit** if the use case is low risk or there is no personal data. Answers are **stored as documentation**; if the author must redact personal data from logs or add guardrails, the platform **advises how** and the author **documents how the risk is managed**. **Advisory, not gatekeeping**; privacy tier (`local`/`cloud_no_data`/`cloud`) is the GDPR proxy. *(Added by ADR-0019, #21.)*
- **License policy** — the platform's **component license policy** (ADR-0022, #23): one coherent stance across four kinds (components / models / vendored UIs / published things), each with per-kind rules. Platform components are governed by the three computed tiers — **`bundled`** (open + must keep the platform repo shippable as Apache-2.0; copyleft only as a separate process that doesn't contaminate platform code), **`listed`** (every dependency licensed + open, contribution-repo license consistent with dependencies, no Apache-2.0 requirement), **`third-party`** (recommend only, cannot enforce); reject no-clear-license and commercial-forbidden/revenue-capped *software libraries*. **Models** carry a five-question **model compliance profile** and hard-block forbidden uses. **Vendored copyleft** is acceptable as a separate process (no fork/embed; derivatives stay copyleft). **Published things** are two-regime: platform services/impls inherit the strict OSS bar; a builder's generic app/API/agent/tool chooses its license (SPDX declared + surfaced as a compliance fact). Maintainer/admin decides edge cases; reject-on-ambiguity. *(Added by ADR-0022, #23.)*
- **Model compliance profile** — the five-question record of a model's weight-license terms (ADR-0022 §3, #23): 1 pay-to-use · 2a research-only · 2b commercial/revenue cap · 3 display-model-name · 4 **train-on-output** · 5 fine-tune. Models are installable if weights are downloadable and the profile is clear; the **default catalog offers only commercial-safe weights**; restricted models are installable with explicit acknowledgment; **non-open-weights models cannot run locally**. The platform **hard-blocks** any forbidden use — no internet/LAN publishing on a non-commercial model, no synthetic-data/training-dataset generation on a no-train-on-output model, no fine-tuning a no-fine-tune model. The profile is a **compliance fact** surfaced with each model. *(Added by ADR-0022, #23.)*
- **Leader core / Worker core** — the two roles of the platform core. The **leader** (first machine) runs the authority capabilities: users, keys, secrets, resources, catalog, cross-machine aggregation and updates. **Workers** run only local capabilities (fleet, install, monitoring of their machine) and hold no users/keys. Role is decided at install/join.
- **Machine identity key** — the long random secret a machine's core uses to authenticate to the leader and other cores; issued by the leader at join via a short-lived **join code** shown in the leader's dashboard. Revoking a machine's key removes the machine from the platform.
- **Action context** — the identity stamped on every user-initiated action (action id + user id) and propagated through chained service calls via the action-context header (each service appends itself to the chain). Every service logs actions with their context: per-user visibility, chronological + hierarchical action trails, and attributable outbound calls (connector audit).
- **Callable surfaces** — the three ways a service can be driven: a **human surface** (its own workflow-oriented UI), an **agent surface** (MCP tools), and a **deterministic surface** (its OpenAPI REST API). Every service exposes all three; the contract's base clause.
- **Agent** — a reusable, versioned definition of an agent: model, system prompt, tools, skills. The **interactive/reactive** unit (a loop): flexible, costly, non-deterministic. Declares an **accessible tool set** (which registry tools the agent may search/invoke) and a **preloaded tool subset** (always in the system prompt). Created once, referenced by id from every session. Lives in the Chat + Agents service (family 9 authoring). Contrast with **workflow** (deterministic DAG); the two interoperate and processes graduate from agent → workflow as their variations become understood.
- **Registry entry** — one record in the capability registry: `id` · `type` (`tool | api | agent | workflow | skill | data_source | webapp`) · **one-line description** (the discoverable, prompt-facing summary, carrying the privacy label where applicable: `<name> · <type> · summary · <local|cloud_no_data|cloud>`) · a **reference to the owning service**, which stores the **full definition** (fetched on demand via `load`). A `data_source` entry additionally carries a **`kind` tag** (`chunks` — document-bundle retrieval from the Document service; `graph` — knowledge-graph/structured retrieval from the Knowledge service); natural-language answers are a **`tool`** entry (agentic search/QA), not a data_source. `api` (a published OpenAPI surface) and `webapp` (a published UI; a static site is a simpler webapp) are **published things** registered by the **Publishing service** on publish — **one entry per surface exposed**. Entries are registered by their owning service, on publish for authored entries (discoverable = launchable). Models are never entries. *(Types extended by ADR-0019, #21.)*
- **Stable name** — a capability/tool entry's canonical name `<service>.<capability>` (e.g. `document.parse`, `audio.stt`, `knowledge.resolve`); an authored entry's `<service>.<kind>.<user-chosen-name>` (e.g. `chat.summarizer`, `workflow.monthly-brief`); a data source's `document.<bundle>` / `knowledge.<kb>`. A published name is a **stable, immutable reference** workflows and agents resolve against. The full catalog grammar adds the implementation level: `<service>.<capability>.<implementation>` (implementation is in the name/catalog, out of the default resolution name unless deliberately split).
- **Name authority** — the leader core's registry, which at **registration time** validates a name against the grammar, **reserves** it (creating the unique entry record), and **rejects collisions** with `409 conflict`, guaranteeing global uniqueness. Validation/reservation at registration only — never request-path enforcement.
- **Search/load tool** — the standard registry surface: `search(query)` → one-line descriptions (scoped to the caller), `load(entry_id)` → the full definition (fetched from the owning service). A **hardcoded core primitive** (bootstrap necessity — you can't discover the discovery tool), not itself a registry entry. Workflows do not search; they resolve explicit stable names.
- **Accessible tool set / Preloaded subset** — the two registry-scoping fields in an **agent definition** (ADR-0007 §9): the **accessible tool set** is which registry tools the agent may search/invoke (the allowlist, living in the agent definition, not the registry); the **preloaded subset** is a subset of accessible, always in the system prompt. The registry enforces the accessible set **server-side** on both `search` and `load`. Workflows have **no allowlist** (they name tools deterministically).
- **Dependency declaration** — a service's declared dependency on another capability/implementation, in **two flavors** (both valid): **loose** — on a *capability* (`llm.chat`), needing at least one implementation that the **end user chooses** at install/use from a dynamically-populated UI list (privacy labels shown) — contributes a *choice* to the placement simulation; **specific** — on a *specific implementation* (`llm.chat.llama3-8b`), a **hard fit constraint** (ADR-0008 §11): it must fit or the dependency is unsatisfiable (service degraded until a machine hosts it), the user does not silently substitute, and any escape is an explicit user re-choice. Feeds the dependency-graph/activity model (capability = dependency unit, implementation = user's choice).
- **Composition primitive** — the tiny set of externally-invoking operations a workflow program uses: **`call`** (a service capability; OpenAPI-first, MCP-fallback), **`model`** (a raw model call with structured output — no natural-language interface), **`agent`** (run a native agent to completion), **`subworkflow`** (run another workflow), **`delay`** (timer), **`event`** (information-system event), **`user_input`** (human input/signal). Branch, loop, and transform are plain Python control flow, not primitives.
- **Abstract request** — a serialized declarative pipeline sent to a service for optimized execution where the data lives. E.g. a workflow builds a **DocETL** pipeline expression natively in Python and sends it to the **Knowledge service** (the DocETL engine, #24 / ADR-0010), which optimizes and executes it — dispatching **faithful-representation** steps to the **Document service** where the raw data lives — the "database engine for unstructured data" (SQL/LINQ-to-SQL analogue). Two execution modes (ADR-0010): **simple execution** (ad-hoc, no optimizer, default model) and the **stored procedure** (define once + calibration dataset + eval metric → offline optimization → a stored, versioned, reusable plan). The result is itself addressable as a data source, so requests compose (the result of a request is a relation you can query again).
- **Representation (faithful)** — an *easier way to consume the exact content* of a document/bundle: office/PDF/HTML form, image form, markdown form, the different ways to **split** the content, **contextualized splits**, raw structured-data extractions, and **embeddings for all of these**. Representations carry **no reflection or interpretation** — a human who can read/see/listen can glance and verify a representation matches its source. Representations span **every modality** (the Image service contributes captions + photo embeddings; the Audio service transcription + speaker diarization + audio embeddings), are stored together in **document bundles**, and their **embeddings are aligned in one vector space** so retrieval works across modalities. The **Document service** produces and indexes representations; **anything beyond them** — choosing a representation for a task, summarizing, thinking, cross-checking even within a bundle — is interpretation, the **Knowledge service's** job. The DocETL engine dispatches each pipeline step by this **representation-vs-interpretation** rule (ADR-0010). *(Added by the DocETL engine ticket, #24.)*
- **Ontology** — the *blueprint* of a domain: **classes/entity types** (Person, Organization, Topic) + **object properties/relation types** (works_for, participates_in) + **validation rules/constraints**. It is the single blueprint that both **grounds** (the types entity resolution matches against) and **shapes raw extraction** (the schema a raw structured extraction must conform to). Several ontologies coexist; each is importable as JSON and/or auto-extracted from a dataset (an auto-extracted ontology is a draft the human reviews before it is versioned). Contrast: a **taxonomy** is a strict tree, a **controlled vocabulary** a fixed allowed list; an ontology is the graph-shaped model that supports reasoning. *(Added by the entity-resolution/grounding ticket, #25.)*
- **Knowledge base** — the *instances*: a named collection of canonical **entities** conforming to an ontology (the entity repository). Several knowledge bases share one ontology (one "Contacts" ontology → a "personal network" KB + an "Acme vendors" KB). Resolution is scoped to **one chosen knowledge base** per call. *(Added by #25.)*
- **Entity repository** — the Knowledge service's store of canonical **entities** (the `knowledge.entities` capability): entities each with a stable **canonical ID**, canonical name, aliases, and class, grouped into **knowledge bases**. *(Added by #25.)*
- **Entity resolution** — the act of resolving an extracted mention to a **canonical entity ID** within a chosen knowledge base (`knowledge.entities.resolve`), deduping mentions/canonicalizing across documents. An *operation* on the entity repository, not a separate capability. Distinct from **entity linking** (mapping a mention to an *external* KB like Wikidata — most home concepts are NIL, so we resolve against our own KBs, not external ones). *(Added by #25.)*
- **Knowledge graph** — the *edges*: **facts** (subject → object property → object) referencing entities by canonical ID, each with **provenance/evidence** (which `document.<bundle>`, which source span). Stored as vertex/edge tables in the Knowledge service's SQLite DB; retrieval backed by the registry's `graph` data_source kind. *(Added by #25.)*
- **Canonical ID** — the stable, immutable identifier of an entity, formatted **`entities.<ontology>.<kb>.<opaque>`** (ontology, then KB, then an opaque token). The canonical name and aliases are separate, mutable fields; the ID never changes on rename or merge. On a merge the survivor keeps its ID and the merged-away ID becomes an alias/pointer to it, so no reference breaks. *(Added by #25.)*
- **NIL** — a mention for which **no** matching entry exists in the knowledge base; the honest "no such entity here" outcome (a pending/new-entity proposal) rather than a wrong guess. *(Added by #25.)*
- **Validation rules / constraints** — declarative, human-authored business rules attached to an **ontology** (e.g. "amount must be ≥ 0", "total = sum of line items", "if `invoice_number` present then `date` and `amount` mandatory"). Evaluated by a **deterministic rule engine by default** (an LLM/classic-AI-assisted option is explicit); violations flow into the **review queue** as proposed items, resolved **human-or-agent** (fix manually / validate exception with a comment / reject the data sample). *(Added by #25.)*
- **Review queue** — the Knowledge service's HITL surface holding **proposed items** (new/ambiguous entities, facts/edges, and validation violations) awaiting a human decision: approve / reject / skip / create-new, each showing evidence (source span + score + why). Graduated policy: uncertain/new items default to human review; high-confidence unambiguous matches auto-commit only under an explicit user-set threshold. Every annotation is learning signal for the extraction model / an agent that may replace the human in the loop. *(Added by #25.)*
- **Resolution scoping** — resolution is always against **one knowledge base, chosen explicitly by the caller**; multi-KB pipelines chain explicit per-KB resolve steps; cross-KB placement is a separate, explicit user question, never a heuristic (mirrors the explicit implementation choice pattern). *(Added by #25.)*
- **Grounding** — tying an extracted mention/statement to a specific, checkable canonical entity/fact (with evidence) rather than free-floating text; the Knowledge service's grounding capability is entity resolution against the concept repository plus knowledge-graph building. *(Added by #25.)*
- **Resolve-then-ground** — the pipeline by which the DocETL engine (#24) grounds a document: extract (schema-constrained by the ontology) → resolve (to canonical entity IDs via `knowledge.entities.resolve`, scoped to a KB) → propose (matched link; NIL and facts go to the review queue) → approve → commit (new entities to the KB, facts/edges to the graph) → validate (the ontology's rules, violations to the review queue). *(Added by #25.)*
- **Explicit implementation choice** — the model-backed step explicitly names the implementation it uses (local or cloud-gateway); the implementation carries its **privacy tier**, so choosing the implementation *is* the privacy decision. There is **no inference policy**, no per-step override, no automatic cloud fallback — a refused implementation surfaces and the user re-chooses (ADR-0007).
- **Agent workspace** — a persistent host directory that is the durable state of a stateful agent: files, plus any packages installed by the user. Independent, addressable resource (own id); survives container destruction; mountable into a session's container. Shared with the Development service (VS Code, JupyterLab open the same directories). Directory + quota are allocated by the platform core's `resources` capability; content is the services'.
- **Harness home** — the persistent home directory of a harness image (e.g. `~/.hermes`, `~/.pi/agent`, opencode's config dir): the harness's own sessions, config, and tool accept/refuse decisions, in its native format. Opaque to the platform — persisted and snapshotted, never parsed. Mounted into every session container of that harness, alongside the workspace. Contrast: platform-native agents (MAF harness) keep structured sessions in the service DB.
- **Agent session** — the binding of an agent + an optional workspace: one run, with conversation history and run state. Stateless sessions (no workspace) run the harness in-process; workspace sessions run in a disposable container.
- **Harness image** — a container image bundling one version of an agent harness (the agent loop + its native tools: bash, file ops) with a base OS and python packages. Not user-configurable in v1; the platform manages image versions and downloads. User packages are installed in the workspace or at session startup instead.
- **Machine (node)** — a physical PC/workstation (e.g. a gaming PC with an NVIDIA GPU) that hosts one or more services, or a rented cloud host. The platform runs on multiple machines and multiple disks per machine. Each machine runs one platform core (leader or worker).
- **Client machine** — the user's remote **command center**: where the install is launched and from where the user starts / uses / stops / updates / monitors / backs up the leader and worker machines. Runs the **resident launcher**. An **additional role any machine can play**, orthogonal to leader/worker — a machine is (leader **or** worker) **and optionally** client. v1: Windows desktop only (macOS, Linux desktop later). *(Added by ADR-0014, #7.)*
- **Resident launcher** — the desktop GUI (Windows) / headless service (Linux) installed on **every machine**; the single surface to start / stop / update / monitor / backup the platform, locally (on this machine) or remotely (any other). On **Start** it opens the web dashboard in the browser. Owns a **machine registry** (this-machine / LAN / cloud entries; cloud holds provider API credentials in the client's secure store); **WoL** wakes sleeping LAN machines (the client does the waking; the target's auto-starting launcher boots the platform); physical power for local machines stays manual, cloud VMs are API-controlled. The registry is **seeded from the leader's catalog**. *(Added by ADR-0014, #7.)*
- **Installer (single-click)** — the native Windows `.exe` (download-button entry, no command line) / Linux `curl …|bash`. Runs the guided install as a **phased progression**: native scripts → Python TUI (via a small streaming **installer API** that runs, interprets and shows progress from stdout/stderr) → **web UI** once the core + dashboard are up (embedded webview on Windows, then opens the dashboard; remote/SSH prints the URL). Carries exactly the **bootstrap**, then leaves the **resident launcher** behind. *(Added by ADR-0014, #7.)*
- **Hardware capacity** — per-machine facts: **capacities** (supported technologies — CPU: AVX2/AVX512, core count; GPU: tensor-core generation, FP8/NVFP4 support — yes/no), **quantities** (measured free RAM/VRAM/disk GB, kept current by monitoring), and a **speed rank per resource** (fast/medium/slow, from lightweight benchmarks run at join — disk read/write, CPU, RAM bandwidth, GPU compute/latency). Facts, never config. The platform's view of "free" = measured free minus active **reservations**.
- **Inference provider** — the external side of inference: where a service's cloud-sourced models actually run (a cloud API owned by a provider — OpenRouter, OpenAI, Anthropic, Google, Meta, Qwen, DeepSeek, Kimi, GLM, HuggingFace, Ollama, Nous portal, fal, ElevenLabs, MixedBread/LightOn, …). A provider may be pay-per-token (metered) or a fixed-price subscription with opaque usage caps (see **billing mode**). Access to a provider is delivered as a **cloud-gateway implementation** of the Inference service's capability; the provider's metadata lives in the **provider registry** (leader-core config); its credentials live in the core's `secrets` capability (master copy + distribution). Includes the user's own existing keys/subscriptions (bring-your-own-key) and provider **bundles** that offer models *and* tools in one subscription. Each service chooses per deployment; cloud is the fallback when local hardware is insufficient. Shapes: docs/adr/0006.
- **Cloud-gateway implementation** — an **implementation** of an Inference service capability (`llm` / `diffusion` / `classic AI`) that fronts external model providers rather than a local engine. Same capability surface as a local implementation (near-identical API/UX). Layer-1 software (LiteLLM and/or direct provider SDKs) + a thin platform layer on top; installed/loaded/unloaded like any implementation, on the **leader machine only** (v1, no HA); any machine's model-backed service can call it over the LAN/overlay. Carries extra concerns: key management, optional input/output data filtering, usage limits, privacy guarantee. LiteLLM is a swappable engine inside it, not a universal hop.
- **Provider registry** — the leader-core configuration holding the platform's providers: `id`, `base_url`, an `api_key` ref into the `secrets` vault, enabled modalities, **privacy tier**, and bundle flag. Adding a provider = adding a row, not code. Popular services ship as **preconfigured, thoroughly-tested templates** (verified against the provider's real current API); an arbitrary **OpenAI-compatible endpoint** is an advanced option. The core **distributes** the resolved provider set to consuming services (Inference for model legs, Connectors for bundle tool legs) via the secrets pattern, but **never enforces it in the request path**.
- **Privacy tier** — a property of each implementation (model implementation / provider leg) describing where data goes and with what guarantee; exactly **three tiers**, labeled **`local` / `cloud_no_data` / `cloud`** platform-wide (ADR-0008): (1) **`local`** — your own machines (local, or a cloud host on your private overlay — data never leaves your control), (2) **`cloud_no_data`** — a cloud service with Zero Data Retention (ZDR / `data_collection: deny`), (3) **`cloud`** — a cloud service with any other policy. Documented prominently on the API/MCP docs, discoverable in the API/MCP description, and displayed on the UI; the **user chooses implementations manually and is warned** (no hidden auto-routing). Choosing an implementation *is* the privacy decision. *(There is **no inference policy** — the earlier `local-only`/`local-then-cloud`/`cloud-only` routing vocabulary is abolished by ADR-0007; these labels replace the earlier `own machines`/`ZDR`/`other` names. ADR-0006 §7, amends ADR-0002.)*
- **Billing mode** — a provider capability bills **one of two exclusive ways**: **metered** (pay-per-token; the service records `usage.cost` per call, the core pulls + aggregates) or **opaque subscription** (fixed price, capped per unit of time; the service counts tokens only, and the **core pulls remaining-% from the provider** — data flow reversed — and distributes the red-line down to services for local enforcement). At the cap, cloud calls return `429 resource_exhausted` with resource **`cloud-spend`** (ADR-0005 §9). LiteLLM's per-key budget is the **enforcement backstop** for metered caps only, and only where the route goes through LiteLLM.
- **Bundle** — a provider offering models *and* tools in one subscription (e.g. Nous portal); modeled as **one provider row with capability-tagged legs**: model legs feed Inference via `models.toml`, tool legs register as MCP tools (#20) and execute via the Connectors service (#18); **one credential covers all legs**.
- **Model** — a runnable artifact of any kind the platform manages: LLMs (GGUF Q4_K_M default), diffusion models (image/video), embedding/rerank transformers, speech models (STT/TTS), and classic PyTorch/sklearn models. Weights cached in RAM for fast load/unload on demand.
- **Model selection goal** — the user's preference for choosing among supported models: `accuracy` / `size` / `speed` / `balanced`. Drives which model a service marks `recommended`; combined with the machine's hardware it also determines `supported`. A per-service install-level setting, changeable from the dashboard.
- **Implementation** — a concrete way to deliver a capability: solves the same problem with different tradeoffs (size/speed/performance, specific data domains or use cases); very similar API, not necessarily identical — the capability's API is the **union of its implementations' variants**, with a documented per-implementation support matrix. **Models are implementations of the llm/vlm capability.** What gets downloaded, loaded, unloaded, deleted. Layer 2 of the two-layer installation (layer 1 = services/capabilities software). Declares **resource requirements** (required technologies, disk at install, **running formula**) and a max capacity (context, batch, document size) capped by machine hardware at load. **Services and capabilities declare the same requirements as implementations.**
- **Resource requirements** — declared by every resource consumer — service, capability, implementation — in two states: **at install** (disk GB + required technologies, yes/no per hardware capacity) and **when running** (RAM/VRAM GB as a **running formula**: the declared configurable variables — batch/concurrency, context length, document/media length, with ranges — and the formula estimating RAM/VRAM/disk from them; resident weights are part of the running estimate, so there is no separate "loaded" number). The **fit check** (can it be installed here?) uses the formula at **minimum parameters**; a load **books** the formula at the **configured parameters**. The configurable variables are the **fit lever**: when a load doesn't fit, the platform proposes lower settings (within the hardware-capped ranges — max context / image size / sound length) before asking to unload anything. Declarations also carry a **performance class** per resource used (fast/medium/slow/any) and **transfer-speed needs** between resources (e.g. high disk→VRAM for fast loads; low-latency RAM↔GPU for realtime) — soft placement clues for the topology's simulation, shown as the reason for a placement.
- **Activity** — a pre-configured set of capabilities in a dependency + concurrency graph; the **user-facing install unit** (more than a profile — a real graph). Selecting an activity installs its capabilities' implementations (gated by fit) and places them via the simulation; several implementations per capability can be installed and switched at runtime in the UI.
- **Dependency graph** — the graph connecting a capability/implementation to the capabilities or specific implementations it depends on (required or optional; **model-backed capabilities are the special case** of a dependency on an llm/vlm implementation). Declares **proximity** per edge (same-machine for realtime/low-latency chains, LAN-ok otherwise) and **concurrency** per edge in three explicit levels: **`always load jointly`** (atomic residency — the group loads/unloads together, a member is never alone resident; install fit = sum, hard) · **`load jointly if possible`** (preferred joint residency — calling one member tries to bring the group, falling back to alone when space is tight; install fit = sum, individual fallback) · **`load on demand`** (fully independent; install fit = largest only). Concurrency feeds the **install-time fit test** only; at runtime every member is an independent implementation — load/unload treats them alike.
- **Working set** — the set of implementations the user's current activities **want** — the demand surface, not the resident set: a live dashboard surface, auto-populated by activity launches; members load when free capacity permits, load **on demand** when it doesn't, are auto-cleared by an idle timeout (default ~30 min, per-capability adjustable; **pin** keeps resident), and are manually drivable (drag = move an implementation between machines — constraints enforced, refusals explained; delete = unload + free disk). **Resident** = the loaded subset, booked in the reservation ledger. Placement of the working set is the topology's answer to model routing (ADR-0004 §5–6).
- **Reservation** — a booking on a machine's free-capacity ledger. Loading an implementation books its install disk + running formula at the configured parameters; unloading releases. The ledger feeds fit checks, dashboard gauges, and eviction decisions.
- **User reservation** — a booking made without declarations: the admin sets a per-user quota limit (disk/RAM/VRAM); the user books within it from the dashboard (workspace disk, notebook/program RAM/VRAM) and releases it manually — the platform never auto-releases a user reservation.
- **Two-layer installation** — layer 1: services/capabilities software (the leader gets all services and capabilities, no questions; workers get only the non-core services their activities need, installed as part of the activity); layer 2: implementations, installed per activity need, gated by fit (a machine gets a capability's local implementation only if the smallest supported local implementation fits — otherwise cloud-only for that capability on that machine). *(Sharpened by the update/versioning flow, #10 / ADR-0016 — the versioning scheme, catalog of versions, and update/rollback mechanics.)*
- **Version** — the identity of a released artifact in the platform's update story, **per tier** (ADR-0016): **Tier 3 platform bundle** = a date-based version (`2026-07`) identifying a coherent set of interdependent service+core+bootstrap versions; **Tier 2 service** = **semver** (its list of capabilities + each capability's API & UI); **Tier 1 implementation** = the **artifact's own version** (engine release, model release, harness image tag). *(Added by the update/versioning flow, #10 / ADR-0016.)*
- **Platform bundle** — the user-facing unit of Tier-3 (core + bootstrap) versioning: a date-based version (`2026-07`) that identifies a **coherent set of interdependent service+core+bootstrap versions**. The **single version the user sees** and updates as a unit; per-service semvers and per-implementation versions live beneath it as the bundle's contents. *(Added by #10 / ADR-0016.)*
- **Capability API version** — the version of a single capability's API (the substrate of the whole versioning scheme), built from **required features + optional features** (e.g. an LLM API may have *image input* or *reasoning levels* as optional features). **Backward compatible within a major** (may only add optional features / compatible changes); **a change to the required set is a major bump**. *(Added by #10 / ADR-0016.)*
- **Update lane** — one of the three distinct update paths the platform drives (ADR-0003 + #10 / ADR-0016): **① host layer** (WSL, Linux distro, virtual disks — updated by re-running the **bootstrap updater**, native per-machine) · **② services** (updated by the core's `install` capability, per-service, independent) · **③ the platform core itself** (self-updates through its own install machinery + the re-runnable bootstrap as recovery). Every lane is **user-triggered and one-click — no automatic updates**; the two behaviors differ in cadence/coordination, not autonomy (Tier 1 = frequent/safe one-click; Tier 2+3 = bundled one-click). *(Added by #10 / ADR-0016.)*
- **Centralized updates list** — the leader-centralized, **persistent** list of available updates the platform keeps adding to (weekly model, new service version, new bundle), which the user browses regularly and acts on with **individual one-click updates at their own pace**. An item is removed when acted on or when the version it refers to is **superseded**. The dashboard's **Install & Updates** surface renders it (leader-only). *(Added by #10 / ADR-0016.)*
- **Data location** — a platform data volume on a user-chosen physical disk, **named after the disk**; standard folders inside (`models/`, `workspace/`, per-service data). Roles are folders, not disks; software lives in the distro's filesystem; no shared/networked storage in v1 (data lives where its service lives). Backup isolation = the `workspace/` folder.
- **Front door** — the tiny static-config reverse proxy on the leader machine (Caddy/nginx class; no logic, no DB, no keys — bootstrap-installed, **not** the core): the one stable address (mDNS name, e.g. `wordslab.local`) for the dashboard and every service UI/API wherever the instance lives (LAN or overlay); one port, one TLS certificate (local CA, distributed to client machines). Makes client machines on the LAN first-class consumers and keeps the core out of the request path.
- **Spec (the destination)** — the complete platform design, written down in repo docs so that building becomes mechanical execution. The deliverable of this effort. Its anatomy is settled (ADR-0013): a **numbered `docs/spec/` tree** (README master index → overview → foundations → one chapter per service → lifecycle → dashboard), written **user-guide-first** and generated in **two passes** — pass 1 = each service's **use cases** (Part 1 of its chapter, decomposed into capabilities across services), pass 2 = each service's **build spec** (Part 2, gathering every requirement the use cases surfaced). Chapters **cite ADRs, never restate them**; the ADR is the source of truth.
- **Use case** — a realistic user journey, **attached to one home service** (where the user's experience starts) even when its implementation reaches into supporting services. The unit of **pass 1**: each use case is **decomposed** into the capabilities it needs in the home service and in supporting services, each with its **impact on that service's callable surface**. Use cases are how features are *designed*, from the experience outward. *(Added by the spec-anatomy ticket, #12 / ADR-0013.)*
- **Decomposition** — the act of breaking a **use case** into the capabilities it requires: in the home service plus in each supporting service, recording the **callable-surface impact** on each. A use case's implementation almost always spans several services; decomposition is how a single user journey generates build requirements across them. *(Added by the spec-anatomy ticket, #12 / ADR-0013.)*
- **Evaluation** — the **systematic measurement of the quality/behavior of a versioned, published artifact** (ADR-0020, #16), at home scale an on-demand activity the builder runs on *their own* published thing (a model-backed implementation, or any published agent/skill/workflow/api/tool/webapp). Works in tandem with the Publishing service. Human-gated: the mechanics are automated, the judgment stays human, and the LLM-as-judge is validated against human labels. *Deliberately NOT centralized* (ADR-0003); lives in the **Training and Evaluation service**. The process draws on the Shankar/Husain *Analyze–Measure–Improve* lifecycle (reference docs in ADR-0020). *(Added by #16 / ADR-0020.)*
- **Evaluation run** — one execution of the evaluation pipeline (dataset → simulate → annotate → judge → report) against a **versioned published artifact**. Rounds are re-run as the builder iterates on the artifact; successive versions' results are compared and the **history is kept in the project repo** as durable proof. *(Added by #16 / ADR-0020.)*
- **Eval dataset** — the input to an evaluation run: a set of inputs simulating user behavior toward the artifact. Sources: **downloaded** (e.g. Hugging Face), **anonymized datasets** from the core's log-extraction (the only real-usage path — always filtered+anonymized, ADR-0020 §5 / the consent model #31), or **synthetic** (personas + target use-cases + source documents → an LLM generates candidate interactions → LLM + human filter → a versioned eval dataset). Grounded on the anonymized real data's dimensions. *(Added by #16 / ADR-0020.)*
- **Open coding / Axial coding** — the two grounded-theory annotation stages in evaluation's `eval.annotate` capability. **Open coding**: the builder reviews the result dataset one by one, writing free-form annotations on what works / what doesn't (the first, most upstream failure). **Axial coding**: clustering those open codes into a small set of **binary failure modes**, forming a structured **rubric**, then annotating more records against it. Both happen in the **generated, task-specific annotation UI**. *(Added by #16 / ADR-0020.)*
- **LLM-as-judge** — an LLM prompted to **score** a result dataset against the (now-known) failure-mode rubric, automating the *scoring of known failure modes* — never the *discovery* of what's failing (that stays human). It is **validated against the human labels** from open/axial coding (train/dev/test splits, precision/recall) before it is trusted. An **explicit implementation choice** (ADR-0007) with its privacy tier surfaced — **local by default**, cloud explicit. *(Added by #16 / ADR-0020.)*
- **Data consent & handling model** — the platform-wide, GDPR-aware model for how data may leave one user's private sphere and enter a builder's/admin's sphere, mediated through the core (#31, open; consumed by evaluation/training, ADR-0020 §5). A user's own prompt/input history is **private to them** (access/review/delete on demand, no other user sees it); builders/admins access real usage only **filtered** (secret/private stripped) and **anonymized** (personal data) via the core's log-extraction — the single mediated boundary ("better to fail to improve/fix than expose a life-altering secret"); per-interaction consent **defaults to "may use for improvement"** with a **very visible "private/secret — do not use" toggle** on every user input; and **anonymization is mandatory before any trace enters a dataset** (GDPR), best-effort via data replacement, never degrading eval/training quality. Impossible-to-anonymize cases are out of v1 scope (user's responsibility). *(Graduated from #16 to its own ticket #31.)*
- **Data sphere** — the unit of data attribution and backup (ADR-0021, #22): a physical user has **three identities, one per sphere** — `laurent` (user), `laurent-builder` (builder), `laurent-admin` (admin); every datum stored by the platform or its services is linked to an identity **and** its role. **User sphere** = the user's own interaction traces with services and uploaded documents/images (private by default, no other user sees them). **Builder sphere** = everything produced *as a builder* (authored workflows/agents/skills, published things, eval datasets/runs, trained models) — **no personal/secret data** (the core mediates the user→builder transition, #31); simulated interactions run as the builder identity, so builder traces need **no filter/anonymize**. **Admin sphere** = **single** (even with several admins): config for the installed core + services, the history of changes, performance metrics and errors — **no user data appears in it**. Backups are organized **per sphere**. *(Added by #22 / ADR-0021; the attribution model itself is folded into #31.)*
- **Backup policy** — the per-sphere configuration a user/admin sets for automatic backups (ADR-0021, #22): a **backup target** (a data location — external disk / another machine's `workspace/` / cloud) and a **cumulative-uptime cadence**. An admin is **compelled to configure a policy + target for each sphere at install** (same-disk allowed as a start, with a persistent UI reminder at every platform start until an off-disk policy is in place); once configured, backups run **automatically** — full every 20h of cumulative uptime, true-incremental every 1h, keep 5 fulls ⇒ hourly recovery points across the last ~100h of uptime. *(Added by #22 / ADR-0021.)*
- **Threat model (home)** — what the platform's security defends against (ADR-0017): a **compromised/malicious agent or harness** (the primary surface) and **accidental data leakage** (a mis-configured connector or `cloud` implementation carrying data out); with explicit boundaries — a **host with OS-level malware** is not fully defended, a **disk thief** is only lightly defended (see **secrets at rest**), and **trusted LAN peers vs untrusted internet crossings**. *(Added by #14 / ADR-0017.)*
- **Host-filesystem isolation** — the platform's outermost security boundary: the platform runs in a WSL VM and gets **no access to host OS files by default**; file sharing is **explicit only** — a dedicated host directory is mounted into the Linux distro and mapped to a Windows drive on the host. A compromised agent inside the platform can only see the shared workspace, not the host's Documents/Desktop/etc. Mount mechanics are installer territory (#7); the default-deny stance is #14's. *(Added by #14 / ADR-0017.)*
- **Secrets at rest** — protecting the platform's credential copies on disk (the #14 half of the #19/#14 boundary; #19 owns storage/distribution/rotation): **light obfuscation** with a static key in the platform source (so a casual disk browser doesn't read API keys in plaintext), **not** strong encryption — harnesses/tools store their own keys in plain `.env` files anyway, so strong at-rest is theater. The **real defense is short-lived, rotated credentials** (ideally ~1 month validity where providers allow) via the #19 rotation machinery — a stolen credential expires fast regardless of disk readability. *(Added by #14 / ADR-0017.)*
- **Container network policy** — the backstop for harness tool calls: agent-session containers (OS-isolated, not VMs) get **default-allow-but-scoped-to-need** outbound (PyPI/GitHub/HuggingFace, the platform's own services/registry/connectors door) but **no unrestricted host or LAN access** — even if the harness approves a tool call, the container can only reach what the policy allows. *(Added by #14 / ADR-0017.)*
- **Connector approval** — the human-approval gate over **send/mutate** connectors (x, github, outlook, huggingface); read-only connectors (web, youtube watch) are logged-only. Approval is **caller-identity-scoped, never platform-wide** — the grant rides the action-context (user + service chain) and is checked against that caller, so approving GitHub for one user does not let another agent/workflow post without its own approval. *(Added by #14 / ADR-0017.)*
- **Guardrail (data-safety)** — the platform's cheap, **on-by-default, visible** safety layer at the two boundaries: **outbound personal-data leakage** (to `cloud` implementations / connectors) and **inbound prompt-injection** (from retrieved/web/ingested data). Need not be purely deterministic — may mix a trained classifier / entity-extraction model / very small LLM, light enough to run in-line. **Never silently filtered** (interception surfaced + adjustable); per-account, admin-configurable. The Shieldstral-class 3B LLM moderation filter is an **optional heavy tier, off by default** (may need a whole machine). *(Added by #14 / ADR-0017.)*
- **Update authenticity** — how the platform verifies what it installs/updates, split across **two supply chains** (ADR-0017): the platform's **own code** (maintainer's repo) is **signed + checksummed against an embedded key**; external **open-source packages** (downloaded by platform scripts at install from PyPI/Ollama/NVIDIA/etc., never embedded) are gated by the **audited supply-chain scan + 1-week wait** (plus upstream checksums where available) at the update metadata/check step (ADR-0016). *(Added by #14 / ADR-0017.)*

## Standing requirements (platform-wide)

- **License policy** — every library and model used by the platform must have a clear open-source license (revenue-threshold restrictions acceptable for models, e.g. "< $10M/month", but **rejected for software libraries**); nothing without a clear license or with commercial use forbidden in the platform's own stack. Resolved by **ADR-0022** ("Define the platform's component license policy", #23).
- **Supply-chain audit** — every library is checked and monitored for known vulnerabilities with an audit trail before being included; **always wait at least a week** before including the latest version of a tool or library. Owned by "Define the security model for the trusted home environment" (#14).
- **Heavy-dependency coordination** — services are designed and evolved together on **shared versions of the heavy dependencies** (PyTorch/CUDA class) so the one-filesystem install dedupes them (uv hardlinks); workspace environments install their own copies by design (decoupled from the platform version, more disk). ADR-0004 §12, ADR-0002.
