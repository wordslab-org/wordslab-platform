# The machine: core, topology, resources

> **Status:** concept chapter assembled from sections 2 and 5 of the architecture overview — the machine, what surrounds the services. **Source of truth:** ADR-0003 (platform core, bootstrap layer, trust), ADR-0004 (multi-machine topology), ADR-0005 (resource management layer), ADR-0014 (single-click install experience). This chapter cites, never restates.

A Wordslab installation is a **fleet of machines** — your PCs, possibly a rented cloud box — running **services** (independent, composable components, each with its own database, business logic, UI, and API, and each able to run fully standalone — the unit of independence, no shared monolith), a **platform core on every machine**, a **bootstrap layer** below everything, and a **front door**. One machine is the **leader** (single, no high-availability in v1); the others are **workers** that join via a short type-in code. The leader's dashboard is the platform's single human front door (ADR-0015).

## The platform core & trust (ADR-0003)

One core service per machine — a small control service (`fleet`, `install`, `catalog`, `resources`, `backup`, `users`, `keys`, `secrets`, `monitoring`, `logs`, `stats`, `datasets`). The core **centralizes control only, never the request path, business logic, or data** (ADR-0003): not business logic, not DBs, not the model lifecycle, not raw logs, not backup data, not security mechanics, not data residency. The core is the platform's eyes, hands and ledger — it never routes user traffic (except dashboard login), never proxies model calls, never enforces quotas in the request path; a service runs fine with the core down.

Every machine runs one core. The first machine's core is the **leader core** (runs the authority capabilities: users, keys, secrets, resources, catalog, aggregation, updates). Other machines run **worker cores** (local capabilities only: fleet/install/monitoring) and hold no users/keys. Same service, same code — capabilities enabled per role.

**Trust is per-machine identity keys** issued via a join code — no PKI, no shared cluster secret, no public ports ever. Every machine's core authenticates to the leader and other cores with a long random key issued by the leader at join (short-lived **join code** shown in the leader's dashboard, typed or scanned by the user); revoking a machine = deleting its key. The join code is the only shared secret; afterwards every machine has its own key. Home LAN = plain HTTP + Bearer (trusted environment). Any **internet crossing** (rented cloud hosts) = the machine joins an **overlay network** (WireGuard-based; Tailscale as the friendly default, self-hosted WireGuard as the no-third-party option) and exposes **no public ports** — the rented machine is never opened to the internet.

## The bootstrap layer (ADR-0014)

Native, platform-specific machinery *below* the service contract — not a service: **no API, no daemon**. The native installer/updater installs/updates WSL + a Linux distro + virtual disks on user-chosen physical disks, installs uv + Python, verifies network reachability, installs the first version of the platform core, then hands off. It persists only as a **re-runnable native updater** for its own layer (host updates); no resident daemon. The install experience is a familiar native installer (no command line), fully guided, transparent about every change, leaving decisions to the user, ending with a recap.

## The front door (ADR-0004)

A tiny static-config reverse proxy (Caddy/nginx class — no logic, no DB, no keys; bootstrap-installed, **not** the core) hosted on the leader machine, giving the one stable address clients use — an mDNS name like `wordslab.local` → the dashboard and every service UI/API, wherever the instance lives (LAN or overlay). One port, one TLS certificate (local CA); clients only ever need one hostname (DHCP-proof). The catalog regenerates its config when placement changes. The core still never routes user traffic (the proxy is config, not logic).

## Layered installation (ADR-0004)

- **Layer 1 — services/capabilities (software):** the **leader gets all services and all capabilities, no questions**. Worker machines get only the non-core services their activities need, installed *as part of the activity installation* — lean workers, disk saved.
- **Layer 2 — implementations:** installed per activity need, gated by fit — a machine gets a capability's local implementation only if **at least the smallest supported local implementation fits** (disk/RAM/VRAM/compute); otherwise that capability is cloud-only on that machine. (A no-GPU machine therefore has every model-backed capability cloud-only — the "no-GPU cheap" configuration, naturally.)

## Topology (ADR-0004)

Leader + workers; the leader can be a cloud node (a single rented no-GPU VPS *is* a whole single-node platform). **v1 = single leader, no HA** — no failover, no election, no replica; if the leader machine dies everything keeps working (services are standalone; worker cores keep monitoring their own machines), only the **authority surfaces** go dark: dashboard login, users/keys/secrets management, new installs, updates, catalog/aggregation views. Recovery = a guided rebuild (re-run bootstrap on a new leader, workers re-join with fresh join codes, services re-register, users and outside-world secrets re-created); services' own per-service Bearer keys survive untouched.

**Placement is a simulation, user-confirmed** — deliberately **no auto-scheduler** (a scheduler is exactly the kind of black box the soul forbids). The simulation resolves an activity's graph: pick implementations (recommended per hardware + model selection goal), check fit, enforce privacy tiers as a hard constraint (a **`local`** implementation never lands on cloud nodes), spread concurrent capabilities across machines, and offer cloud when nothing local fits — with cost shown. One-click confirm → implementations download/load → the **working set** populates. It is re-runnable on demand as needs or the fleet evolve.

**Routing is the placement's outcome**, visible per call. A model-backed call = a dependency on an llm/vlm implementation; routing is which loaded implementation serves the call, chosen by the graph's placement (same machine as the caller first, else the machine where the working set placed the implementation, least-loaded tiebreak, offer a cloud implementation when nothing local fits — an explicit user choice, never an automatic fallback, ADR-0007). No per-call knob, no hidden load balancer; the routing table is the working set's placement. Every call records "served by: machine · implementation · model" in the action trail.

**Data lives in data locations** — volumes named after physical disks, with **roles as folders** inside: the bootstrap creates one platform data volume per user-chosen physical disk, named after that disk (visible — "D:", or the disk's real name; no "volume #2" abstraction); standard folders inside — `models/`, `workspace/`, plus per-service data folders. Roles are folders, not disks — a big HDD can hold models while an NVMe holds workspace. Software lives in the distro filesystem only (one filesystem → uv dedup and docker layer sharing). **No shared/networked storage in v1** — each machine's disks are local to it; data lives where its service lives. Cross-machine movement = backup/restore or reinstall.

## Resources (ADR-0005)

Every resource consumer — **service, capability, implementation** — declares the same resource requirements in **two states**:

- **At install:** disk GB (weights + execution code) + required **technologies** (yes/no per hardware capacity — AVX2/AVX512, tensor-core generation, FP8/NVFP4, etc.).
- **When running:** RAM/VRAM GB as a **running formula** — the declared configurable variables (batch/concurrency, context length, document/media length, with min/max ranges) and the formula estimating RAM/VRAM/disk from them, **capped by hardware** (max capacity — context length in tokens, batch/concurrency, max document size — capped by machine hardware at load and can be lowered by user config). Resident weights are part of the running estimate; there is no separate "loaded" number.

The platform's view of "free" is **measured free minus active reservations**: a **reservation ledger** tracks bookings against measured capacity. Loading an implementation **books** its install disk + running formula at the configured parameters; unloading **releases**. Disk is booked at install time on the `models/` folder before the download starts. The ledger feeds the fit test, dashboard gauges, and eviction decisions. Each machine's capacities are measured facts (never config), with speed ranks per resource from lightweight benchmarks run at join and on demand — a slow NVMe or network disk is not mistaken for fast by its label.

**Eviction is deterministic for the already-done, asked for the genuinely ambiguous** — explicitly **no LRU** (an LRU is the black box the soul forbids). An **idle sweep** unloads members past their idle timeout (default ~30 min, per-capability adjustable; **pin** keeps resident) on the next sweep — their own inactivity, not a choice. Under pressure, first free what's already idle; then **ask the user** when there is genuine ambiguity — if exactly one way frees the needed amount, do it silently; if several distinct ways exist, ask the user to choose, showing each option and what it frees. **Remembered decisions** are explicit per-load rules ("to load X, when ambiguous between A and B, choose A") — stored visibly, editable, applied without asking when they resolve the ambiguity. Before unloading anything, the platform proposes **lower parameters** for the incoming implementation (within the hardware-capped ranges) to fit — the fit lever. Never pinned implementations, never auto-evicting user reservations.

**Quotas** cover disk and cloud spend:

- **Disk** (ADR-0005): a models quota per data location (each disk's `models/` folder), three layers of caps enforced at the tightest — per data location, per service folder, per user. **Two-tier enforcement:** platform-mediated writes (uploads, implementation downloads/installs) are **blocked at quota** (`429 resource_exhausted`, `disk`); everything else (service-internal DBs/indexes, agent/user programs) **can't be blocked** — enforcement is **monitor + warn + a strong storage UI**: green/orange/red gauges with clear attribution of who oversteps (warn ~80%, red at 100%); the human acts.
- **Cloud spend** (ADR-0005): two parallel local dimensions — a **pay-per-token monthly money cap** (set on the dashboard; cloud-enablement proposes a visible default) enforced locally at call time, and **fixed-price subscriptions with opaque usage limits**, where the provider owns the limit and exposes a **"% usage remaining per unit of time" API**; provider adapters plug into that remaining-% API, the platform caches remaining-% (refresh on a cadence + opportunistically — no per-call round-trip) and shows each plan as a measured gauge with thresholds (orange below ~30%, red below ~10%). "Can I route to cloud?" respects whichever local limit is tighter; at the cap, cloud-routed calls return `429 resource_exhausted` with resource **`cloud-spend`**; local-only traffic is unaffected. Caps are **distributed, enforced locally, accounted by pull** (the ADR-0003 secrets pattern — master + distribution, no call-time round-trip); the core never sits in the request path.

⚑ *ADR-0004's original two-level concurrency vocabulary (`co-resident`/`swappable`) was replaced by ADR-0005's three explicit levels (`always load jointly` / `load jointly if possible` / `load on demand`); 0004's glossary text is not visibly amended. Read 0005 as canonical.*
