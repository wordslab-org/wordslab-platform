# ADR-0002 — Service template & contribution surface (embodies the contract)

**Status:** accepted (resolution of wayfinder ticket "Define the service template & contribution surface"); amends ADR-0001 (base contract item 9, callable surfaces); **amended by ADR-0004** (implementations layer; heavy-dependency coordination), **ADR-0006** (privacy-tier vocabulary → three-tier data-class taxonomy), **ADR-0007** (inference policy removed from the service declaration; callable-surface mapping clarified), **ADR-0008** (privacy-tier labels → `local` / `cloud_no_data` / `cloud`), **ADR-0024** (the template gains a required learning/operability bar declaration — documentation, skills+MCPs, diagnostics, graded by depth) and **ADR-0027** (implementation-declaration model — one declaration mechanism `implementation.toml`; `models.toml` retired; engines and models both implementations, a model declaring its engine dependency)

> **Evolution (ADR-0031 — declaration model v2):** §5 below is superseded in five places. (1) A **service has no implementation** in the capability sense — `service.toml` describes the service; `implementation.toml` describes capability implementations only; the repo ships **two templates** — `service-template/` and `implementation-template/` — instead of a service-kind `implementation.toml`. (2) **`families` is no longer declared in `service.toml`** — family contracts are API-documentation facts, not identity; the conformance suite parameterizes via a test-side manifest (#70). (3) The **`[[capabilities]]` list is enriched** — each capability declares name/description/version, its API path prefix, required/optional, and UI menu elements + entry points; the service declares one service-level disk/RAM requirement for its own API+UI code. (4) **`[ranks]` is removed** (no cross-contributor ranking; benchmark drift) — model implementations declare objective facts only, quality metrics are fetched from artificialanalysis.ai at selection time (ADR-0031 §5). (5) `[engine-dependency]` is superseded by **generic dependencies** (capability or specific implementation, ADR-0031 §4). The decision text stays as its historical record.

> **Evolution (2026-09, Inference service design, #35 / ADR-0029):** the template's "capabilities own routes and UI pages" wording is sharpened by the **service-as-stable-shell** refinement. A service's own implementation is a **stable shell**: it holds the service's UI and the shared contract entry points (`/health`, `/api`/OpenAPI, `/mcp`, one auth) **plus the stable declaration of its capability list and each capability's API description** (`service.toml` capabilities + per-capability API surface). This shell is the stable, learnable-once face that composition and references resolve against. Everything behind the shell — which capabilities are present, which implementations realize them, which models/engines are installed — is the personalizable, swappable inner world. Capabilities own the routes/UI of their own surface; the service's routes/UI above them are the stable shell. *(Detail in ADR-0029 §4.)*

> **Evolution (ticket #275 — the template ships a template-level contract-checker):** the template's capability set is not only the proof canary. It also carries the **control-placement map + the placement-invariant harness** (`contract/placement_map.toml`, `contract/placement.py`, harness at `tests/support/placement.py`) as a **data-surface capability** (`placement`) that indexes ADR-0017's security model — every threat frame → its named control(s) → the single owning home — so placement is asserted continuously rather than rediscovered at the end (the build order's testability rule). It declares a full `[<service>.<capability>]` section like any capability — `api` names the service's own API description document `/openapi.json`, since the capability contributes no fragment to that document and so has no capability path to name (ADR-0031 §2 defines `api` as the capability's API description entry point); `ui.menu` ships empty (it has no UI) — so it is visible in the catalog and carries the same learning bar as any capability. The map is **data, never a declaration key**: a `[security]`/`[placement]` table in `service.toml`/`implementation.toml` is an unknown key, exactly as a declared `[learning]` table is (§7's amendment). The map cites ADR-0017 as its single source; each control's runtime *stance* is the verification substrate's (#276), not this checker's.

## Context

ADR-0001 defines what every service API must be; the template is how a service comes to exist as code. Easy contributions are a stated goal: the template and a contributor guide are the community's front door. The platform ships its services in one repo (`wordslab-platform/services/`), is contributed by a single person for the foreseeable future, and simplicity is the main feature — everything here is cut to that.

## Decision

A new service is a folder in `services/<name>/` in the wordslab-platform repo, produced by **copying `template/`** at the repo root. No generator CLI. The per-domain repos (wordslab-voice, wordslab-images, wordslab-llms, wordslab-webscraper) are **out of scope** — stale studies, ignored entirely, not archived or touched.

### The template (what a service looks like as code)

1. **Self-contained (vendored contract).** `src/<service>/contract/` holds the base contract machinery (`base/`: auth, errors, pagination, health, idempotency — always kept, never edited) and the nine family modules (`families/`: keep what `service.toml` declares, delete the rest; all nine ship in the template). **No shared SDK package** — services stay fully independent; drift is caught by the conformance suite (`tests/contract/`, vendored with the template, family-parameterized: base always runs, families per declaration). Contract changes flow ADR → template → services, verified by the suite.
2. **Capabilities (sub-services).** A service decomposes into in-process `capabilities/` modules — e.g. audio: stt, tts, vad, voice cloning, realtime voice chat. Each capability owns its business logic, implementation declarations, routes and UI pages, while **sharing the service's contract surfaces** (one `/health`, one auth, one `/mcp`, one OpenAPI) and **one SQLite database** (SQLModel; namespaced tables per capability). Realtime voice needs STT+TTS+VAD in one low-latency loop — separate deployable services would force LAN HTTP round-trips. A capability may later be promoted to its own service. *(Amended by ADR-0004 — implementations layer:* a capability is delivered by **implementations** — concrete ways to solve its problem with different tradeoffs; a capability may have several installed, switchable at runtime. Layer 1 software (services/capabilities) is installed once per machine; layer 2 **implementations** are installed per activity need, gated by fit, and carry resource profiles (disk/RAM/VRAM/compute) with a **max capacity** (context length, batch, document size) capped by machine hardware and lowerable by config. Both the **serving engines** (Ollama, vLLM, sglang, ComfyUI, the cloud gateway) and the **models** they serve are layer-2 implementations — a model declares its engine dependency (ADR-0027); models and engines are implementations of the llm/vlm/ml/diffusion capability pairs. *)*
3. **Callable surfaces (amends ADR-0001, base item 9).** Every service is driven three ways: a **human surface** (its own workflow-oriented UI), an **agent surface** (stateless MCP at `/mcp`), and a **deterministic surface** (the OpenAPI REST API). MCP tools are **auto-generated from the OpenAPI spec** by default (zero drift — the MCP surface *is* the API, machine-translated); service authors override with hand-written `@tool` definitions where the machine-optimized API needs an English-friendly interface. Family 3 (tool services) narrows to `resources`/`prompts` and tool-service semantics.
4. **Human surface.** FastHTML pages (Starlette-based, coexists with FastAPI in one process), client-side interactivity via **Alpine.js** (vendored locally; FastHTML's native Surreal disabled), Pico base styles. All JS/CSS **vendored in `ui/static/` — no CDN** (a home LAN may be offline). A **shared UI kit** (design tokens, components, nav shell) is copied by the template so every service and the dashboard look like one product.
5. **Declaration.** `service.toml` = identity (name/version/description), families, capabilities, UI nav. *(Sharpened by ADR-0018:* implementation declarations are formalized as a named **`implementation.toml`** file per implementation, symmetric with `service.toml` — identity, source (local weights or a cloud provider reference), license, links, download/disk sizes, resource profile, privacy tier. The community-catalog *listing* surface — how a catalog repo points to these descriptions — is ADR-0018's, not re-decided here.)* *(Model-backed implementation choice is explicit per step — an author picks a specific implementation (local or cloud-gateway), which carries its privacy tier; there is **no inference policy** — see ADR-0007.)* *(Privacy tier: the per-implementation three-tier data-class taxonomy from ADR-0006 §7 — own machines / ZDR cloud / other cloud — replaces the earlier `default`/`no-retention`/`no-training` vocabulary; see ADR-0006.)* The API self-declares via `/openapi.json` (base contract). Implementations are declared **per implementation in one `implementation.toml`** (the former per-capability `models.toml` is retired — models are one kind of implementation, and so are the engines that serve them; see the reconciliation in ADR-0027): description, source (**local weights or a cloud provider reference**), license, links (release / repo / license / evaluations), download & disk sizes, resource profile (VRAM formula inputs — weights GB, KV cache per token **at the recommended KV quant**, overhead GB, batch/context params — plus RAM and compute needs), max-capacity inputs (context length, batch, document size), accuracy & speed ranks within the capability's list, input/output modalities, and — for a model implementation — its **engine dependency** (the engine capability + minimum version). **`supported`/`recommended` are computed, never stored** — from the machine's hardware + the model selection goal (`accuracy`/`size`/`speed`/`balanced`, per-service install setting); max capacity is capped by hardware at load and lowerable by user config. *(Amended by ADR-0004 and ADR-0027.)*

6. **Heavy-dependency coordination.** *(Added by ADR-0004.)* Services are designed and evolved together on **shared versions of the heavy dependencies** (PyTorch/CUDA class) so the one-filesystem install dedupes them (uv hardlinks); divergence costs disk. Workspace environments (JupyterLab / agent workspaces) install their own library copies by design — decoupled from the platform version, at the cost of disk (ADR-0004 §8).

7. **The learning/operability bar.** *(Added by ADR-0024; mechanism amended by #75 — see below.)* Every service, capability and implementation carries its learning/operability artifacts — a **required, auditable bar**, enforced at contribution time, graded by depth (**how to use · how it works · study in depth · going further**), covering:
   - **Documentation** — the four depth levels, authored to be readable and indexed for agents: structured Markdown with a canonical section schema + front-matter (title, keywords, MCP tool references). One source, dual-consumed by the human surface and an agent indexer — no separate agent-authored document set.
   - **Skills + MCPs** — MCP tools auto-generated from the OpenAPI spec (with `@tool` overrides where the machine API needs an English-friendly interface) plus a **how-an-agent-drives-me `skill`** (a registry `skill` entry) as a first-class artifact. A capability that genuinely can't be agent-driven records no skill — the honest **"not agent-operable"** convention, not a fake skill.
   - **Diagnostics tools** — to fix problems and optimize behavior. *(Not yet shipped in the stage-0 template — tracked on the bar's own follow-up, ticket #75's stage-0 scope being docs + skill.)*
   The bar's artifacts are **discovered by layout, not declared** (#75, superseding the original per-declaration mechanism): the service template's `service.toml`/`implementation.toml` carry no `[learning]` tables — a subject's docs and skill are found by path + name convention (ADR-0031 §2/§3 as amended). **Mandatory to publish for `bundled`/`listed`; recommended-with-tracked-gaps for `third-party`** (mirroring ADR-0018's computed tiers). Applies to published things' documentation/skills/diagnostics surface too (ADR-0019).

### Contribution surface (solo-first)

`template/` at repo root; copy-to-start ritual (copy, rename, edit `service.toml`, delete undeclared families, implement capabilities) documented in a **short CONTRIBUTING.md checklist**; conformance gate = `uv run check` locally + **one minimal GitHub Actions workflow** on PRs touching `services/`. Community machinery (generator CLI, issue templates, governance) is deferred until real demand — the story is optimized for one contributor today, extensible later. *(The community-catalog *listing* surface — a `platform.toml` pointing at these `service.toml`/`implementation.toml` files (renamed from `catalog.toml` by ADR-0019), and the review/quality-bar/graduation process — is designed in ADR-0018, not here.)*

## Considered options

- **Shared SDK vs vendored contract** — vendored: full independence, one-language readability, no packaging; drift caught by the conformance suite. A shared package would add versioning/coupling for a 6-service home platform.
- **Capabilities in-process vs separate services** — in-process: realtime voice needs STT+TTS+VAD in one loop; one install, one dashboard entry; promotion path kept open.
- **Auto-generated vs hand-declared MCP tools** — auto-generated default guarantees coverage and sync; `@tool` overrides for author-curated interfaces.
- **Surreal (FastHTML-native) vs Alpine.js** — Alpine: mainstream declarative model, large community/docs (matters for contributions); both are script-tag includes, no build step.
- **FastLite vs SQLModel** — SQLModel gives schema/validation/OpenAPI typing the contract requires; FastLite stays for exploration notebooks.
- **Computed vs stored `supported`/`recommended`** — computed from hardware + goal: no stale flags, one truth; model metadata stays factual (ranks, sizes, links).

## Consequences

- Unblocks: v1 catalog (#18, instantiates services from the template), composition (#13, any service callable via MCP), dashboard (#8, UI kit + model/goal management), capability registry (#20, every service registers tools), published apps (#21, a published app is or is not a service — decided there).
- Sharpens: model management (#4 — aggregation of model implementations + resource story), inference providers (#19 — expanded with cloud access machinery: connectors, credentials, billing, quotas).
- Amends ADR-0001: base contract item 9 (callable surfaces); family 3 narrowed.
- The template itself is a build step once the spec lands — the spec's service chapters describe it chapter-and-verse.
