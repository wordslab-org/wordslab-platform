# ADR-0001 — Minimal uniform service contract (base + family contracts)

**Status:** accepted (resolution of wayfinder ticket "Define the minimal uniform service contract"); **amended by ADR-0002** (base item 9 — callable surfaces; family 3 narrowed), **ADR-0004** (family conformance: capability API = union of implementation variants), **ADR-0005** (429 taxonomy: `cloud-spend` resource name) and **ADR-0007** (family 9 authoring shape: agents carry accessible + preloaded tool lists; workflows are Python programs with the composition primitive set)

## Context

The platform's promise is "all service APIs look alike and share the same concepts" — but every service is fully independent (own DB, business logic, UI, API), model-backed, tool-backed, or both, and runs at home scale on trusted hardware. The enterprise studies (architecture_v2.md S.1–S.33, 486 canonical endpoints) encode the full multi-tenant SaaS answer; this contract is the deliberate inverse: the same concepts, radically lighter execution, cut ruthlessly to what home scale needs. Simplicity is the main feature; the contract is the keystone the service template embodies, the dashboard surfaces, and composition consumes.

## Decision

The service contract is **one base contract applying to every service API, plus nine family contracts that a service opts into according to its function**. It is a conformance checklist: a service is a platform service when it implements the base and the families its function requires. Everything not on the list is free (business endpoints, model-specific request bodies, UI, DB, deployment).

### Base contract (every service API, always)

1. **Transport & self-description** — HTTP/1.1 + JSON only; SSE (`text/event-stream`) for streaming; REST-ish plural kebab-case paths under `/v1/<resource>[/{id}]`; every service exposes its OpenAPI 3.1 doc at `/openapi.json`. No gRPC, no binary, no HTTP/2 requirement. Service identity (name, version, families) is reported by `/health` — no separate manifest.
2. **Auth** — `Authorization: Bearer <api-key>` only, per-service API keys generated at install and stored/validated by the service itself (no central round-trip; a service works standalone, cross-machine, or in the cloud). No user accounts inside services — users/auth are platform-core concerns. 401 `authentication_failed` when absent/invalid.
3. **Versioning** — `/v1` path prefix. Additive changes are backward-compatible within a major; breaking changes = new major prefix (`/v2`), old major kept as long as the service chooses. No mandated deprecation windows, no beta headers, no dated revisions.
4. **Errors** — every response carries `X-Request-Id`; error bodies are `{"error": {"type", "message", "resource"?}, "request_id"}`. Fixed 11-code taxonomy: 400 `invalid_request` · 401 `authentication_failed` · 403 `permission_denied` · 404 `not_found` · 409 `conflict` · 413 `request_too_large` · 429 `resource_exhausted` (with `resource`: `vram`/`ram`/`disk`/`gpu`/`cloud-spend`…) · 500 `internal_error` · 503 `busy` · 503 `unavailable` · 504 `timeout`. No rate limiting in v1 (429 means resource exhaustion, nothing else), no 422, no per-endpoint error enums.
5. **Pagination** — cursor-based only: `?limit` (default 50, max 200) + `?cursor`; responses `{"items": [...], "next_cursor": "<opaque>"}`. No page numbers, no offset; cursors never parsed by clients.
6. **Health** — `GET /health` → `{"status", "service", "version", "resources", "models"?}`. Status enum: `starting` · `installing` · `downloading` · `backing_up` · `ready` · `busy` · `full` · `degraded` (needs human maintenance) · `stopping` · `down`. HTTP 200 for alive/progressing states, 503 for cannot-serve states. `resources` = used/total per host: `cpu`/`gpu` (percent), `ram`/`vram`/`disk` (GB); `gpu`/`vram` omitted when no GPU. `models` (model-backed services) = per-model status dict.
7. **Idempotency** — optional `Idempotency-Key` header on mutating endpoints; the service dedupes retries and returns the original result.
8. **Usage accounting (principle)** — responses from operations that consumed a resource (model inference, tool call, cloud round-trip) carry a `usage` field; the unit is family-defined. Services record usage in their own DB; the core aggregates through service APIs — no central usage pipeline.
9. **Callable surfaces** *(amended by ADR-0002)* — every service is driven three ways: a **human surface** (its own workflow-oriented UI), an **agent surface** (stateless MCP at `/mcp`, tools auto-generated from the OpenAPI spec, with author `@tool` overrides for English-friendly interfaces), and a **deterministic surface** (the OpenAPI REST API itself). MCP is no longer optional per function — it is a universal surface.

### Family contracts (a service implements base + the families its function needs)

**Conformance (amended by ADR-0004):** a capability's API is the **union of its implementation variants** — the family contract documents which implementation supports what (a per-implementation support matrix and documented deviations), rather than force-fitting every implementation into one identical shape. Implementations of a capability solve the same problem with different tradeoffs (size/speed/performance, data domains) and may expose very similar but not identical APIs.

1. **LLM & agents inference** — the unique LLM inference service (optionally several instances on different machines with different local models; instance choice is model-routing, not contract) exposes the **OpenAI Responses API by reference** at `POST /v1/responses`: request, typed streaming events, tool calling (function tools + MCP servers), structured outputs, citations, reasoning items, refusals, `usage` in tokens. **Multimodal input is in** (`input_text`/`input_image`/`input_audio`); generation output is text/structured. Rule: follow upstream OpenAI shapes; document deviations, pinned to a reference date. Chat Completions is not required. Engine gap (local engines lag on vision-through-Responses) is absorbed by the service adapter, not a contract deviation — verify Responses+vision on Ollama at template build time.
2. **Other model inference** — **copy the most successful service per modality, by reference**: embeddings `POST /v1/embeddings`, images `POST /v1/images/generations` + `/edits`, audio `POST /v1/audio/transcriptions` + `/speech`, video `POST /v1/videos` + `GET /v1/videos/{id}`. Where no dominant OpenAI shape exists (rerank, OCR, classification, segmentation, classic models, document understanding), copy the most successful OSS service in the niche (TEI for rerank; LightOn/mixedbread-style document APIs). `usage` in the reference API's native unit. The reference API decides sync vs async; the sync/async variant pattern (family 5) applies.
3. **Tool services** — **MCP in stateless mode by reference** (spec 2026-07-28; JSON-RPC 2.0, per-request headers, no sessions), served at `/mcp` on each tool-exposing service; Bearer per base on every request. *(Amended by ADR-0002: the `/mcp` endpoint itself is now a base-contract surface — every service exposes it with auto-generated tools; this family narrows to tool-service semantics: `resources`/`prompts` optional, curated tool definitions, discovery.)* FastMCP reference SDK — must support the stateless transport (verify at build). Discovery: services register `{id, name, one-line description, endpoint, tools: [{name, one-line description}]}` in the platform's **capability registry**; a standard search/load tool pulls full definitions into context on demand (see "Design the capability registry & search/load service", #20).
4. **Realtime (voice)** — the **revised OpenAI Realtime API by reference**: REST session creation → WebRTC peer connection with `oai-events` data channel (primary, what the browser dashboard needs), WebSocket (server-side agents), unified session config object (`{type: "realtime", model, audio: {output: {voice}}, ...}`), same event vocabulary. **MCP tools in-session** supported (references registry capabilities). Cuts: no ephemeral tokens (Bearer), no SIP/telephony, voice-only v1 (no image inputs in realtime), tools-in-realtime rides with composition.
5. **Async jobs & model lifecycle** — **Model lifecycle**: `GET /v1/models` (`{id, supported, recommended, downloaded, size_gb, status}`) · `POST /v1/models/{id}/download` (job) · `DELETE /v1/models/{id}` · `POST /v1/models/{id}/load` / `unload` · `POST /v1/models/{id}/prepare` (→ `{"status": "ready"}` or a job: `unloading previous model → loading new model → warming up → ready`, with `downloading` first when absent). Model status enum: `absent` · `downloading` · `available` · `loading` · `ready` · `unloading` · `error`; `/health` reports per-model. **Jobs**: `{"id", "status": "queued"|"running"|"completed"|"failed", "progress": 0-100, "created_at", "result"?, "error"?}` with `GET /v1/jobs/{id}` (progress on every poll) and `POST /v1/jobs/{id}/cancel`. **Sync/async dual variants** (optional per capability): sync = designed < ~10 s for typical requests; async = same endpoint + `"background": true` → job, minutes, progress, optional webhook. Both may coexist as different implementations for different use cases; the contract fixes the interface, not the internals.
6. **Batch** — `POST /v1/batches` (inline `items: [{id, ...request}]` or a file reference from family 7 for media batches) → job with **per-item status**: the job object embeds `items` for the first 50, then `GET /v1/batches/{id}/items` (base pagination) beyond. `GET /v1/batches/{id}/results` — per-item results keyed by client `id` (custom_id pattern), big outputs as file references. `POST /v1/batches/{id}/cancel`; optional webhook on completion. OpenAI Batch API naming by reference; per-item visibility is a documented deviation (media batches need it).
7. **Uploads** — **OpenAI Files + Uploads API by reference**: file object `{id, name, bytes, mime_type, status, created_at}`; `POST /v1/files` (multipart, small) and resumable `POST /v1/uploads` → `PUT /v1/uploads/{id}/parts` → `POST /v1/uploads/{id}/complete` (huge files, streamed to disk); `GET /v1/files/{id}`, `GET /v1/files/{id}/content` (streaming download), `DELETE /v1/files/{id}`. `file_id` is a first-class input across families 1/2/6. Deviations: retention = keep until deleted (no expiry windows); storage = the service's local disk(s); per-service size limits declared in metadata, no platform cap.
8. **Webhooks** — **Standard Webhooks spec, HMAC-SHA256 shared-secret variant**: `webhook-id` / `webhook-timestamp` / `webhook-signature` (`v1,<hmac>`) headers; event shape `{"id", "type", "created_at", "data"}` (base `job.completed` shared, plus service-specific types); best-effort delivery with ~3–5 exponential-backoff retries, no DLQ (core can query job state to catch up); minimal CRUD `POST/GET/DELETE /v1/webhooks` + `POST /v1/webhooks/{id}/rotate`. No Ed25519/JWKS — that's multi-tenant SaaS machinery.
9. **Authoring & management** — **Agents**: CRUD `/v1/agents` (Mistral Studio Agents & Conversations shape; definition schema from composition). **Workflows**: CRUD `/v1/workflows` with the Studio lifecycle (definition → deployment → run/schedule). **Training**: **Tinker API by reference** — training *sessions* (`POST /v1/training/sessions` `{base_model, method: "lora", rank}`), programmatic steps (`forward_backward`, `optim_step`, `save_state`/`load_state`, `sample`), publish weights → new model in `GET /v1/models`; family 5 jobs underlie it. **Publishing definitions**: Studio deploy-style — versioned agent/workflow → published → launchable. Publishing *agent-generated web apps/services* is a separate decision ("Define how agents publish generated web apps & services", #21). **Management**: platform-core APIs are base-contract services; admin = permission level (admin-scoped key), not a different API family; what is centralized is "Scope the centralized platform services" (#9).

### Deliberately out (deferred, shape reserved)

Rate limiting & `x-ratelimit-*` headers, beta headers & deprecation calendars, batch JSONL data-row semantics (superseded by family 6), citations/reasoning-replay/refusals as transversal clauses (they are LLM-family details), pricing/surcharges, strict-mode schema ceilings, realtime video/screen, telephony/SIP, Ed25519/JWKS webhooks, encrypted reasoning replay, model catalogs as a separate registry (covered by family 5 + model management).

## Considered options

- **Flat checklist vs base + families** — a flat list either over-constrains CRUD services or under-specifies inference. Families chosen: llm/agents inference, other model inference, tool services, realtime, async jobs & model lifecycle, batch, uploads, webhooks, authoring & management. Plain CRUD services get base only.
- **Auth: per-service Bearer keys (chosen) vs shared platform token vs core-issued JWT** — keys preserve service independence (standalone, cross-machine, cloud) at trivial home-scale cost; JWT can come later if users/auth demand it.
- **Responses API vs Chat Completions** — Responses is the modern OpenAI surface (background jobs, MCP tools, typed events); Chat Completions stays an optional compatibility alias.
- **Stateful vs stateless MCP** — the 2026-07-28 spec makes stateless the default; it fits multi-instance, no session machinery.
- **WebSocket-only vs revised Realtime API (WebRTC primary)** — WebRTC is what a browser dashboard needs and OpenAI's direction; on a home LAN no STUN/TURN is required.
- **Ed25519/JWKS vs HMAC shared-secret webhooks** — JWKS exists for multi-tenant key rotation; home scale uses the spec's simple variant.
- **OpenAI fine-tuning jobs vs Tinker training sessions** — Tinker's session-based programmatic shape fits a home researcher (inspectable steps, resume, sample) far better than opaque jobs.

## Consequences

- Unblocks "Define the service template & contribution surface" (#11), which embodies the contract.
- Shapes the dashboard (#8: health/status colors, resource graphs, model management), composition (#13: Responses surface + MCP tools + registry), provider model (#19: config inside services, not wire auth), spec anatomy (#12).
- Spawned tickets: "Design the capability registry & search/load service" (#20), "Define how agents publish generated web apps & services" (#21).
- Open risks for the service template: Ollama vision-through-Responses lag (adapter), MCP stateless transport freshness (pin + verify), WebRTC machinery on LAN.
